# MoonLight Hanwha는 AI를 어떻게 사용하는가

MoonLight Hanwha는 사내 구성원이 **어울리는 모임을 찾고, 대화를 실제 약속으로 옮기는 과정**에 AI를 사용합니다. 모임 추천에서는 개인의 취향과 만남 방식을 해석하고, 약속 추천에서는 채팅에서 나온 요구를 검색된 장소와 연결합니다. 두 기능 모두 백엔드에서 OpenAI `gpt-5.4-mini`를 호출하도록 구현되어 있습니다.

이 문서는 서비스 설명을 위한 문서이며, 현재 저장소의 구현을 기준으로 합니다. 전체 기능은 [기능 명세](features.md), 운영 설정은 [배포 절차](deployment.md)를 참고하세요. 실제 배포 환경의 API 호출 성공 여부는 별도 확인이 필요합니다.

## 1. AI에 전달하는 context란 무엇인가

여기서 **context(맥락 정보)**는 AI가 이번 추천을 판단할 수 있도록 서버가 골라 요청에 담는 자료입니다. 매 요청마다 필요한 데이터를 다시 구성합니다. 모델이 사용자의 전체 활동을 계속 기억하거나 사내 데이터베이스를 직접 조회하는 구조는 아닙니다.

| 사용 순간 | 해결하려는 문제 | 요청에 담는 context | 서비스에서 사용하는 결과 |
| --- | --- | --- | --- |
| 매칭 탭에서 모임 조회 | 내 취향과 원하는 관계에 맞는 모임 찾기 | 저장한 프로필, 후보 모임 요약, 나와 멤버들의 관계를 집계한 수치, 규칙 점수 | 후보 모임 순서와 추천 이유 |
| 채팅방에서 `AI 추천 약속 잡기` 실행 | 대화에서 나온 요구를 실행할 약속으로 정리 | 모임 정보, 요청자의 참가 이후 최근 대화, 카카오 검색 장소, 현재 시각 | 장소·시간·활동·주변 장소와 후보별 이유 |

공통 흐름은 **브라우저 → Supabase Edge Function → 필요한 데이터 조회·정리 → OpenAI → 서버 검증 → 화면 반영**입니다. AI에는 역할과 판단 규칙을 담은 지시문(`system`)과 실제 context를 담은 JSON(`user`)을 함께 보냅니다.

## 2. AI 모임 추천: “나에게 어떤 모임이 어울릴까?”

### 어떤 정보를 사용하는가

프로필은 **마지막으로 저장한 값**을 사용합니다. 입력 중이지만 저장하지 않은 설정은 추천에 반영하지 않습니다.

| context | 실제 전달 필드 | 어떻게 사용하는가 |
| --- | --- | --- |
| 관심사·취미 | `interests`, `hobbies` | 모임 제목·태그와 비교합니다. GPT에는 단어가 달라도 의미가 가까운 활동을 고려하도록 지시합니다. |
| 선호 지역 | `regions` | 서버가 먼저 지역 밖 모임을 제외합니다. AI에도 선택된 지역을 전달합니다. |
| 원하는 규모 | `group_size` | 최소·최대 인원 범위와 내가 참가했을 때의 예상 인원을 비교합니다. |
| 관계 방향 | `matching_preferences.direction` | `deep`은 아는 사람과의 재회, `wide`는 새로운 사람과의 만남을 우선하는 기준입니다. |
| 성별·계열사 선호 | `gender`, `company_id`, `matching_preferences.same_gender`, `matching_preferences.scope` | 같은 성별·계열사 멤버 비율과 함께 전달해 명시한 선호를 고려하게 합니다. |
| 연령대 | `age_band` | 정확한 나이를 `20대 후반` 같은 구간으로 바꿔 전달합니다. 현재 규칙 점수에는 연령 항목이 없고, GPT 지시문에도 별도의 연령 가중치는 없습니다. |
| 모임 기본 정보 | `id`, `title`, `region`, `when_label`, `tags` | 어떤 활동을 어디서, 어느 시간대에 하는 모임인지 판단할 자료입니다. |
| 모임 규모·참가 여부 | `capacity`, `member_count`, `joined` | 정원·현재 인원·이미 참가했는지를 나타냅니다. |
| 관계·구성 집계 | `known_count`, `same_gender_ratio`, `same_company_ratio` | 내가 이미 만난 사람 수, 다른 멤버 중 나와 같은 성별·계열사 비율입니다. 멤버별 프로필 대신 집계값을 보냅니다. |
| 사전 계산 점수 | `rule_score` | 규칙 엔진의 적합도 점수입니다. GPT에는 참고값으로 제공하며, 이 순서를 그대로 따르도록 강제하지 않습니다. |

닉네임·실명·사번·사진·사용자 ID·MBTI는 모임 추천의 전달 필드에 포함되지 않습니다. 채팅 내용과 만남 평가도 이 요청에 넣지 않습니다. 사용자 ID는 서버의 데이터 조회와 캐시 구분에 사용합니다.

### context를 추천 순서로 바꾸는 과정

1. **참가 가능한 후보를 고릅니다.** 서버가 선호 지역 안의 열린 모임을 조회하고, 미참가 모임 중 정원이 찬 곳을 제외합니다. 이미 참가한 열린 모임은 목록에 남깁니다.
2. **규칙으로 1차 순위를 만듭니다.** 관심사·취미와 제목·태그의 겹침 34%, 관계 방향에 따른 아는 사람 비율 22%, 희망 규모 16%, 같은 성별 비율 14%, 같은 계열사 비율 10%, 남은 자리 4%를 사용합니다. 성별·계열사 항목은 해당 선호가 적용될 때만 넣고, 적용한 가중치 합으로 다시 정규화합니다. 계열사 선호는 점수 기준이며, 지역처럼 후보를 제외하는 조건은 아닙니다.
3. **미참가 상위 20개를 GPT가 재정렬합니다.** 위 표의 프로필과 후보 정보, 규칙 점수를 전달합니다. GPT에는 모든 후보를 정확히 한 번씩 배치하고, 입력 근거로 60자 이내 추천 이유와 최대 3개의 주의점을 쓰도록 지시합니다. 입력에 없는 사용자·모임 속성을 추측하지 않도록 명시합니다.
4. **서버가 결과를 검사합니다.** 후보 밖 ID, 중복·누락, 빈 이유, 잘못된 형식이면 규칙 결과로 대체합니다. GPT가 배열 순서를 반환하면 서버가 순위 번호를 붙입니다. 상위 20개 밖의 모임은 규칙 순서를 유지하고, 이미 참가한 모임은 뒤에 둡니다.
5. **화면에 반영합니다.** 서버가 반환한 추천 순서를 모임 목록에 적용합니다. 일반 카드에는 AI 이유·주의점을 표시하지 않고, 모임 상세 시트에서 추천 이유를 확인할 수 있습니다.

### 설명 예시

아래는 동작을 설명하기 위한 가상 사례이며 실제 모델 응답이나 성능 측정 결과는 아닙니다.

> 사용자가 지역은 ‘여의도’, 취미는 ‘러닝’, 규모는 ‘4~6명’, 관계 방향은 ‘넓은 인맥’으로 저장했습니다. 후보 중 ‘한강 조깅 모임’은 현재 3명이고 아는 사람은 0명입니다.

서버는 먼저 여의도 밖의 모임을 제외합니다. 남은 후보가 상위 20개 안에 들면 GPT가 ‘러닝’과 ‘조깅’의 의미적 연관성, 참가 후 4명이라는 규모, 모두 새로운 사람이라는 관계 정보를 함께 고려할 수 있습니다. 이때 “러닝 취미와 맞고, 새로운 동료들과 4명으로 시작할 수 있어요”처럼 입력에 근거한 이유를 생성하도록 요청합니다. 특정 후보가 반드시 1위가 된다는 보장은 없습니다.

## 3. AI 약속 추천: “우리 대화를 바탕으로 어디서 무엇을 할까?”

### 어떤 정보를 사용하는가

약속 추천은 사용자가 채팅방 메뉴에서 실행할 때 호출됩니다. 서버가 먼저 해당 모임의 참가자인지 확인합니다.

| context | 실제 전달 내용 | 어떻게 사용하는가 |
| --- | --- | --- |
| 모임 정보 `meeting` | 제목 `title`, 지역 `region`, 태그 `tags`, 시간대 `when_label` | 모임의 기본 목적과 활동 범위를 정합니다. 대화에 구체적인 요구가 없으면 이 정보를 사용합니다. |
| 최근 대화 `conversation` | 요청자가 참가한 시점 이후의 최신 30개 메시지를 시간순으로 정리한 `speaker`, `text` | 대화에서 언급된 장소·시간·활동 선호를 우선 반영하도록 합니다. 본문은 메시지당 최대 300자입니다. |
| 검색 장소 `places` | 최대 8곳의 이름 `name`, 분류 `category`, 주소 `address` | 실제 검색된 후보 안에서 만남 장소와 주변 장소를 고릅니다. 장소 ID·좌표·링크는 서버가 보관하고 결과 검증 후 붙입니다. |
| 현재 시각 `now`, `now_label` | 한국 시간 기준 시각과 사람이 읽는 날짜·요일 안내 | ‘이번 주 목요일’ 같은 표현을 실제 약속 날짜로 해석하는 기준입니다. |
| 대화 없음 안내 `note` | 대화가 없으면 “모임 정보만으로 제안하세요” | 대화가 없는 상태에서도 모임 정보와 검색 후보로 제안하도록 합니다. |

발신자 ID는 전달 구간에서 처음 등장한 순서대로 `참가자1`, `참가자2` 등으로 바꿉니다. 원래 발신자 ID·닉네임과 개별 메시지 작성 시각은 대화 JSON에 넣지 않습니다. **본문에 사용자가 직접 적은 이름·연락처를 자동으로 찾아 지우는 처리는 현재 없습니다.** 발신자 치환이 본문 전체의 익명화를 보장하는 것은 아닙니다.

참가 전 대화, 다른 채팅방의 대화, 참가자 전체의 프로필, 공유 의견 화면의 제출 내용, 가능 시간표는 이 AI 요청에 포함하지 않습니다. 최근 30개 밖의 이전 합의도 별도로 요약해 전달하지 않습니다.

### 검색과 AI가 맡는 역할

1. **서버가 장소를 검색합니다.** 모임 지역·태그와 첫 태그를 활용한 활동 힌트로 카카오 로컬 검색을 실행합니다. 예를 들어 지역이 ‘판교’, 태그가 ‘보드게임’이면 ‘판교 보드게임’ 같은 검색어를 만듭니다. 현재 검색어 생성에는 채팅 원문을 사용하지 않습니다.
2. **GPT가 후보와 대화를 연결합니다.** 검색 결과와 최근 대화를 한 요청에 넣고, 대화의 요구를 우선 반영하되 검색 목록 안에서 장소를 고르게 합니다. 따라서 대화에 나온 장소가 검색 후보에 없으면 그 장소를 자유롭게 추가하는 방식은 아닙니다.
3. **구조화된 약속을 받습니다.** 만남 장소(`place`), 시간 문구(`time`), 약속 시각(`meet_at`), 활동(`activity`), 주변 장소(`nearby`), 후보 이름·추천 이유(`candidates`)를 JSON으로 받습니다. 후보는 최대 5곳, 주변 장소는 최대 3곳입니다.
4. **서버가 장소와 시간을 검증합니다.** 검색에 없는 후보는 제거하고, 남은 후보에 검색에서 얻은 ID·주소·좌표·상세 링크를 채웁니다. 만남 장소도 남은 후보 중 하나로 맞추며, AI가 제안한 주변 장소는 검색 목록의 이름과 일치해야 남깁니다. 검색 확인은 후보의 출처 확인이며, 영업 여부·예약 가능 여부를 보장하지는 않습니다.
5. **사용자가 약속을 조율합니다.** 결과를 지도와 약속 카드에 표시합니다. 사용자는 후보 장소를 선택하고 시간 조율·의견 수집을 이어 갑니다. 일반 카드의 전원 투표·시간 경과 확정, 공유 의견 수집 후 방장 확정은 서버와 사용자 흐름이 담당합니다.

시간 지시문에는 현재부터 180일 안의 한국 시간 ISO 시각을 쓰고, 정확한 날짜 합의가 없으면 `meet_at`을 `null`로 두도록 명시합니다. 서버는 반환된 시각이 없거나 유효하지 않으면 시간 문구를 다시 파싱합니다. 날짜를 특정할 수 없으면 `null`로 남아 시간 경과 자동 확정 대상에서 빠집니다.

### 설명 예시

다음은 실제 요청 구조를 축약한 가상 예시입니다. 장소 A·B는 설명용 이름이며 실제 검색 결과가 아닙니다.

```json
{
  "now": "2026-09-07T12:00:00+09:00",
  "meeting": {
    "title": "퇴근 후 보드게임",
    "region": "판교",
    "tags": ["보드게임"],
    "when_label": "평일 저녁"
  },
  "conversation": [
    { "speaker": "참가자1", "text": "이번 주 목요일 저녁 7시 어때요?" },
    { "speaker": "참가자2", "text": "좋아요. 처음 하는 사람도 하기 쉬운 게임이면 좋겠어요." }
  ],
  "places": [
    { "name": "장소 A", "category": "보드카페", "address": "판교 지역 주소 A" },
    { "name": "장소 B", "category": "카페", "address": "판교 지역 주소 B" }
  ]
}
```

이 context를 받으면 GPT는 목요일 19시라는 대화와 현재 날짜를 연결하고, 보드카페 후보에서 초보자도 함께할 활동을 제안할 수 있습니다. 예를 들어 장소 A에서 쉬운 보드게임으로 시작하고 장소 B를 전후에 들를 후보로 제안하는 식입니다. 실제 게임 보유 여부나 두 장소의 도보 거리까지 확인하는 기능은 없습니다.

## 4. 오류가 나도 서비스가 이어지는 방식

| 상황 | 현재 처리 |
| --- | --- |
| 모임 추천의 API 키 누락·오류·잘못된 응답 | 규칙 엔진의 순위·이유로 대체합니다. |
| 약속 추천의 GPT 호출 실패 | 검색된 후보와 모임 정보로 기본 약속 카드를 만듭니다. |
| 장소 검색 결과 없음·검색 실패 | GPT를 호출하지 않습니다. 기본 카드와 검색 상태를 표시하고, 대체 검색어가 있으면 함께 안내합니다. |
| 외부 API 없는 로컬 데모 | 준비된 모임·약속 데이터와 로컬 정렬로 시연합니다. 실시간 GPT 추천으로 설명하지 않습니다. |

OpenAI 요청은 응답 본문 수신까지 20초, 출력 최대 4,000토큰으로 제한하고 실패 시 재시도 없이 대체 결과를 제공합니다. 모임 추천은 서버 인스턴스별 최대 100개의 성공 결과를 60초간 캐시합니다. 캐시 키에 사용자·정리된 프로필·후보 전체를 포함하므로 관련 데이터가 달라지면 다시 계산합니다. 브라우저도 60초가 지난 뒤 매칭 탭에 진입하면 목록을 다시 조회합니다.

## 5. 데이터 처리와 현재 AI 활용 범위

OpenAI API 키와 카카오 REST 키는 서버의 Secret으로 관리합니다. 브라우저에는 비밀 키를 두지 않습니다. 두 AI 요청 모두 허용된 필드만 구성하고, 입력의 제목·태그·대화·장소명에 포함된 명령을 따르지 말라는 지시와 JSON 형식 검증을 적용합니다.

API 요청에는 `store: false`를 지정합니다. 실행 기록에는 사용자·모임 식별자, 모델, 성공·대체 여부, 소요 시간, 오류 유형을 남기고 서버 로그에는 입력·출력 토큰 수를 기록합니다. AI 실행 로그에는 프롬프트·응답 원문을 남기지 않지만, 서비스 동작에 필요한 기존 채팅과 생성된 약속 카드는 데이터베이스에 저장합니다.

만남 후 **별점과 코멘트는 향후 추천 개선용 데이터로 수집**합니다. 평가 시점의 모임 정보, 평가자 설정, 아는 사람 수, 같은 성별 비율, 약속 생성 출처 등을 특성 스냅샷으로 저장하며 `ai_training_examples` 뷰에서 조회할 수 있습니다. 이 저장용 스냅샷에는 나이·MBTI도 포함되어, 위의 실시간 모임 추천 입력과 구성이 다릅니다.

현재 별점으로 모델을 재학습하거나 추천 가중치를 자동 조정하는 기능은 없습니다. 평가 데이터를 두 AI 요청에 넣거나 자동으로 OpenAI에 보내는 경로도 없습니다. 서비스의 개인화는 **그때의 저장된 설정·관계 집계·최근 대화를 요청 context로 구성하는 방식**입니다. 가능 시간 교집합 계산, 투표 집계, 실명 공개, 홈 행성 점등도 각각 일반 프로그램 로직으로 처리합니다.
