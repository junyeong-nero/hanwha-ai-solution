# 입장 시도 제한 (#16)

`0017_login_attempt_limit.sql`을 먼저 적용한 뒤 `demo-login`을 배포합니다. IP·계정(계열사+정규화한 사번) 각각 최근 10분 20회이며, DB 잠금으로 검사와 기록을 함께 수행합니다. 제한 저장소 오류 시 입장을 허용하지 않습니다. 키는 SHA-256 해시이고 하루 지난 기록은 다음 허용 요청 때 정리합니다.

기본값은 전달 헤더를 신뢰하지 않고 IP를 `unknown` 공유 버킷으로 처리합니다. 따라서 기본 배포는 **전체 10분 20회**로 보수적으로 제한됩니다. 발표 인원이 많으면 아래 검증을 마친 후 `DEMO_LOGIN_TRUSTED_PROXY_HOPS`를 설정해야 합니다.

- 직접 접근 경로가 없고 모든 요청이 동일한 신뢰 프록시를 거치는지 확인합니다.
- 별도 테스트 환경에서 서로 다른 `x-forwarded-for`를 보냈을 때 게이트웨이가 실제 주소를 오른쪽에 어떻게 추가/덮어쓰는지 확인합니다. 확인한 고정 프록시 개수만 환경변수에 설정합니다(예: 실제 주소 하나를 덧붙이면 `1`). 헤더 원문은 운영 로그에 남기지 않습니다.
- 헤더가 없거나 잘못되면 공유 버킷으로 제한하며 `cf-connecting-ip` 같은 다른 헤더로 우회하지 않습니다.
- 헤더 앞부분을 바꿔 21회 요청했을 때 21번째부터 `429 RATE_LIMITED`인지 확인합니다. 계정을 고정하고 IP를 바꾸는 경우도 동일하게 차단돼야 합니다. 공유 네트워크는 IP 한도를 공유합니다.

신뢰 경계 기준은 [MDN X-Forwarded-For 보안 지침](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For#security_and_privacy_concerns)을 따릅니다(2026-09-07 확인). 실제 Supabase 배포의 헤더 처리 방식은 배포 전 위 절차로 확인해야 합니다.
